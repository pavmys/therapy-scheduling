# 0002. Тести: чисті функції й server actions з підміненим Supabase

- Статус: прийнято
- Дата: 2026-10-22
- AC: усі AC-HOLD-01 … AC-HOLD-36 (назви тестів починаються з AC ID)

## Контекст

`npm run ac:coverage` рахує AC «реалізовано» лише за непропущеним тестом у `*.test.ts(x)`, який запускає `npm test`. Job `app` у CI працює без бази; `db-check` лише застосовує міграції на одноразовій базі. Зміна `.github/` — окреме рішення.

## Рішення

- Доменна логіка (статуси, 24 години, «Past», день і тиждень у America/Los_Angeles, валідація й нормалізація email) — чисті функції в `src/lib/**` з параметром `now`; юніт-тести Vitest з фіксованим часом.
- Server actions — тести з `vi.mock("@/lib/supabase/server")`: фейковий клієнт віддає роль і результат або код помилки (`23505`, `SLOT_UNAVAILABLE`, …); тест перевіряє повідомлення PM і аргументи запиту.
- Атомарність і RLS гарантує база (ADR 0001); у PR кожної задачі з міграцією — ручна SQL-перевірка (анонім, користувач без профілю, therapist, некоректні дані), результати в описі PR, плюс сценарії AC на Preview.

## Розглянуті варіанти

- Інтеграційні тести проти Postgres (`supabase db start`) окремим workflow — надійніше для AC-HOLD-04, AC-HOLD-36 і RLS, але зміна `.github/`, довший CI; відкладено.
- E2E (`tests/e2e/*.spec.ts`) — `ac:coverage` їх не рахує, доки немає окремого кроку CI.

## Наслідки

- Тести швидкі й працюють без секретів і бази.
- Помилку в SQL-функції тести не впіймають — ризик закриває ручна перевірка; при першому такому інциденті — новий ADR про інтеграційні тести.
